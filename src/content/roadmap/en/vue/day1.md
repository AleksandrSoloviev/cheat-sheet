    title: "What is reactivity in Vue 3?"
    body: "#### Short answer\n\nReactivity is Vue's mechanism that **itself** tracks two things: who read this field, and whom to notify when the field changes. You do not manually say \"re-render\", and you do not list deps the way you do in `useEffect`.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nimport { ref, computed } from 'vue'\n\nconst count = ref(0)\nconst doubled = computed(() => count.value * 2)\n\ncount.value++ // trigger → the UI / computed update on their own\n// in the template: {{ count }} {{ doubled }} — no .value\n</script>\n```\n\n#### Phrase to recite\n\nVue's reactive system is a Proxy around state: reading a field registers a dependency, and writing notifies subscribers (render, computed, watch). The UI updates on its own, without a manual deps list like in React.\n\n#### React bridge\n\n| What | Vue | React |\n| --- | --- | --- |\n| Who knows the dependencies? | The framework (track on read) | You (`useEffect(..., [deps])`, memo) |\n| What happens on setState / a change? | Trigger → only the subscribers of that field | Re-render of the component function (and down the tree, unless there is memo) |\n| Mutating `obj.x = 1` | With `reactive` it is fine, Vue will see it | Usually it will not see it — you need a new object / setState |\n| \"Reactive system\" | Built in (Proxy + scheduler) | No equivalent; there is reconciliation after render |\n\nThe React formula: **UI = f(state)** → you called `setState` → the component ran again. The Vue formula: **the data itself calls its subscribers** → only the dependent computed values, watchers, and pieces of the DOM update.\n\nFull answer: the Vue conspect → Q1\n"

    title: "`ref` vs `reactive` — when to use which?"
    body: "#### Short answer\n\n`ref` is a universal wrapper for any value (a primitive or an object), accessed through `.value`. `reactive` is a Proxy around an **object**; you cannot put a primitive in it. In practice: counters, flags, and \"replace the whole value\" → `ref`. A local form of related fields → `reactive`. Out of a composable you usually return a `ref` or `toRefs`.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\n// A predictable public API — refs\nexport const useCounter = (initial = 0) => {\n  const count = ref(initial)\n  const inc = () => { count.value++ }\n  return { count, inc } // count stays reactive for the consumer\n}\n\n// If reactive is convenient inside — expose toRefs\nexport const useForm = () => {\n  const form = reactive({ name: '', email: '' })\n  const reset = () => { form.name = ''; form.email = '' }\n  return { ...toRefs(form), reset }\n}\n</script>\n```\n\n#### Phrase to recite\n\n`ref` is a wrapper with `.value` for anything, including replacing the whole value. `reactive` is an object Proxy, convenient for forms, but destructuring breaks reactivity, so a composable usually returns `ref` or `toRefs`.\n\n#### React bridge\n\n| What | Vue | React |\n| --- | --- | --- |\n| Primitive | `ref(0)` | `useState(0)` |\n| Object | `ref(obj)` or `reactive(obj)` | `useState(obj)` + usually an immutable update |\n| Replace the whole value | `x.value = next` | `setX(next)` |\n| Mutate a field | with `reactive` — fine | usually `setX(prev => ({ ...prev, field }))` |\n| Destructuring state | with `reactive` it breaks reactivity | `const { n } = state` in render — fine (the next render gives a new value) |\n| Custom hook return | return `ref` / `toRefs` | return values + setters |\n\nIn React one `useState` covers both a primitive and an object. There is no \"depth\" of reactivity — only a new state reference, which means a re-render. In Vue you choose the **shape** (`ref` vs `reactive`) and you have to remember the Proxy.\n\nFull answer: the Vue conspect → Q2\n"

    title: "Why does `ref` have `.value`?"
    body: "#### Short answer\n\n`ref` is a wrapper object `{ value: T }`, not the value itself. In script, without `.value` you are working with a reference to the wrapper, not with the data. In the template Vue automatically unwraps top-level refs, so you do not write `.value` there.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nconst count = ref(0)\nconst state = reactive({ n: 1 })\n</script>\n\n<template>\n  <!-- unwrap: this is count.value -->\n  <p>{{ count }}</p>\n  <button @click=\"count++\">+</button>\n\n  <!-- reactive is already without .value -->\n  <p>{{ state.n }}</p>\n</template>\n```\n\n#### Phrase to recite\n\n`.value` is required because `ref` is a wrapper object: that is how Vue can track primitives. In script we write `.value`. In the template, top-level refs unwrap on their own.\n\n#### React bridge\n\n| What | Vue `ref` | React `useState` |\n| --- | --- | --- |\n| Storage | `{ value: T }` | the value `T` in the fiber + a setter |\n| Read in logic | `count.value` | `count` |\n| Write | `count.value = 1` | `setCount(1)` |\n| In the UI | template unwrap / JSX `count` after destructure | `{count}` |\n| Reference stability | the `count` wrapper is stable | `setCount` is stable; `count` changes every render |\n\nIn React you have a bare value plus a required setter. In Vue there is one entity, `ref`, and `.value` is an explicit get/set that the system can intercept.\n\nFull answer: the Vue conspect → Q3\n"

    title: "What is losing reactivity? How do you fix it?"
    body: "#### Short answer\n\nLosing reactivity is when you pull a field out of `reactive`, props, or a Pinia store with ordinary destructuring and get a raw value with no Proxy and no link. Fix it with `toRefs` / `toRef` / `storeToRefs`. For props, know the classic pattern and the Vue 3.5+ caveat about reactive props destructure.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\n// Classic (always a safe interview answer):\nconst props = defineProps<{ id: string }>()\nwatch(() => props.id, load)\n// or\nconst id = toRef(props, 'id')\nwatch(id, load)\n\n// Vue 3.5+ reactive props destructure:\n// the compiler can turn the destructure into reactive local bindings\nconst { id } = defineProps<{ id: string }>()\n// id stays linked to props — BUT this depends on the version and flags;\n// in an interview: \"I know the 3.5 feature, in production I check the version; the classic answer is toRef / a getter\"\n</script>\n```\n\n#### Phrase to recite\n\nLosing reactivity is destructuring `reactive`, a store, or props into a bare value. It is fixed with `toRefs` / `toRef` / `storeToRefs`. For props the reliable pattern is a getter or `toRef`. Vue 3.5 destructure is pleasant sugar, and you should know which version you are on.\n\n#### React bridge\n\n| Situation | Vue | React |\n| --- | --- | --- |\n| `const { id } = props` | Before 3.5, or without compiler magic — a risk; the classic fix is `toRef` | Normal: the next render brings a new `id` |\n| `const { count } = store` | Breaks Pinia state reactivity | Depends on the store; in Zustand a selector is often `useStore(s => s.count)` |\n| Update model | A subscription to the field | A re-render of the component function |\n\nIn React, destructuring props is safe because reactivity means calling the function again. In Vue, reactivity means a subscription to a specific access. Pulling the value off the Proxy or ref breaks that link.\n\nFull answer: the Vue conspect → Q4\n"

    title: "`computed` vs `watch` vs `watchEffect`?"
    body: "#### Short answer\n\n`computed` is a pure derived value with a cache. `watch` is explicit sources plus a side effect: it is lazy, and you get old and new values. `watchEffect` is an effect with automatic dependency tracking, and it runs immediately. For a UI value, use computed. For requests and localStorage, use watch or watchEffect.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\n// computed — a pure value\nconst fullName = computed(() => `${first.value} ${last.value}`)\n\n// watch — an explicit source, a side effect\nwatch(\n  () => props.id,\n  async (id, prevId, onCleanup) => {\n    const data = await api.getUser(id)\n    user.value = data\n  },\n  { immediate: true }, // like useEffect on mount and on change\n)\n\n// deep — when you need nested fields of an object\nwatch(\n  form,\n  () => { saveDraft(form) },\n  { deep: true },\n)\n\n// watchEffect — deps come from reads inside the callback\nwatchEffect(() => {\n  document.title = title.value // read title → subscribed\n})\n</script>\n```\n\n#### Phrase to recite\n\n`computed` is a cached derived value. `watch` is an effect on explicit sources, with old/new and the `immediate` / `deep` options. `watchEffect` is an auto-tracked effect that starts immediately. For the UI, use computed. For side effects, use watch.\n\n#### React bridge\n\n| Vue | React (a close anchor) |\n| --- | --- |\n| `computed` | `useMemo` (a cached value) |\n| `watch(source, cb)` | `useEffect(cb, [deps])` + explicit deps |\n| `watchEffect(cb)` | `useEffect` with no deps / auto-tracking you keep in your head — but React deps are manual |\n| `immediate: true` | the effect already runs after mount |\n| `deep: true` | you usually compare new objects yourself, or with JSON, or a deep-compare library |\n\nThe formula: **computed = a value**, **watch\\* = an effect**. In React both often live in `useEffect` / `useMemo`, and the boundary between a value and an effect is the developer's discipline.\n\nFull answer: the Vue conspect → Q5\n"

    title: "How do you clean up inside `watch`?"
    body: "#### Short answer\n\nReturn a cleanup function from the `watch` / `watchEffect` callback. Vue calls it before the next run of the effect and when the watcher stops. The typical case is an `AbortController` for fetch. This does not replace `onUnmounted` for the whole component. It is cleanup **of this specific effect**.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nwatch(id, (newId) => {\n  const ctrl = new AbortController()\n\n  fetch(`/api/users/${newId}`, { signal: ctrl.signal })\n    .then(r => r.json())\n    .then(data => { user.value = data })\n    .catch(err => {\n      if (err.name === 'AbortError') return\n      // error handling\n    })\n\n  // called before the next watch run and when the watcher stops or unmounts\n  return () => ctrl.abort()\n})\n</script>\n```\n\n#### Phrase to recite\n\nIn `watch` I return a cleanup function. Vue calls it before the next effect tick and when the watcher stops. For fetch I use an `AbortController`. That is cleanup of the effect, not a full replacement for `onUnmounted`.\n\n#### React bridge\n\n| Vue | React |\n| --- | --- |\n| `return () => cleanup()` from `watch` | `useEffect(() => { ...; return () => cleanup() }, [id])` |\n| abort when `id` changes | abort in the effect cleanup |\n| `onUnmounted` | cleanup of the same `useEffect` with no deps, or a separate effect |\n\nThe model is almost 1:1 with React: the effect restarts, so the previous one is torn down first.\n\nFull answer: the Vue conspect → Q6\n"

    title: "Why `watch(() => props.id, ...)` and not `watch(props.id)`?"
    body: "#### Short answer\n\nAt the moment you call it, `props.id` is already a primitive snapshot. `watch` receives a number or a string and does not know where to read it from again later. You need a getter, a `ref`, or `toRef`, so that each run reads the current value and tracks the dependency.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nconst props = defineProps<{ id: string }>()\n\n// ❌ snapshot: watch(props.id) ≈ watch('42') — the source is not reactive\nwatch(props.id, (id) => {\n  load(id) // when props.id changes, the callback often will NOT run\n})\n\n// ✅ getter: on every track it reads props.id again\nwatch(() => props.id, (id) => {\n  load(id)\n})\n\n// ✅ toRef — a ref linked to props.id\nwatch(toRef(props, 'id'), (id) => {\n  load(id)\n})\n\n// ✅ if you already have a ref\nwatch(idRef, load)\n</script>\n```\n\n#### Phrase to recite\n\n`watch(props.id)` passes a snapshot of the primitive. To follow changes you need `watch(() => props.id)` or `toRef(props, 'id')`.\n\n#### React bridge\n\n| Vue | React |\n| --- | --- |\n| `watch(() => props.id, cb)` | `useEffect(cb, [props.id])` |\n| `watch(props.id)` — a snapshot bug | in deps you still put an expression that is read again on every render |\n| `toRef(props, 'id')` | there is no separate equivalent — the deps array |\n\nIn React the component function runs again, and the deps are compared again. In Vue `setup` runs once, so the source for `watch` has to stay live (a getter or a ref).\n\nFull answer: the Vue conspect → Q10\n"

    title: "Options API vs Composition API — what to choose, and why?"
    body: "#### Short answer\n\nThe Composition API (plus `<script setup>`) is the Vue 3 standard for new logic: better reuse through composables, TypeScript, and grouping code **by feature** rather than by option type. The Options API still lives in legacy code and in simple components. You must be able to **read** it. New code is usually Composition.\n\n#### Code example\n\n```\n<script>\nexport default {\n  data() {\n    return { query: '', results: [] }\n  },\n  computed: {\n    hasResults() { return this.results.length > 0 }\n  },\n  watch: {\n    query(q) { this.fetch(q) }\n  },\n  methods: {\n    async fetch(q) { /* ... */ }\n  },\n  mounted() {\n    this.fetch(this.query)\n  }\n}\n</script>\n```\n\n#### Phrase to recite\n\nThe Composition API is the Vue 3 standard: logic by feature, and composables instead of mixins. You should be able to read the Options API for legacy code. It is the same kind of shift as class components to hooks in React.\n\n#### React bridge\n\n| What | Vue | React |\n| --- | --- | --- |\n| Old style | Options API (`data` / `methods`) | Class components |\n| New style | Composition API / `<script setup>` | Function components + hooks |\n| Reuse | composables `useXxx()` | custom hooks `useXxx()` |\n| Antipattern | mixins | HOCs / complicated mixin analogues |\n\nOptions → Composition is approximately class → hooks: the same motivation (logic by feature, and reuse without inheritance).\n\nFull answer: the Vue conspect → Q13\n"

    title: "What does `<script setup>` give you?"
    body: "#### Short answer\n\nIt is sugar over `setup()`: every top-level binding is automatically available in the template. You get the macros `defineProps`, `defineEmits`, `defineExpose`, `defineModel`, and `defineOptions`. There is no `return {}`. There is less boilerplate, and tree-shaking is better. It compiles to a normal `setup()`.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nimport { ref } from 'vue'\nconst count = ref(0)\nconst inc = () => count.value++\n// return is not needed — everything top-level is visible in the template\n</script>\n\n<template>\n  <button @click=\"inc\">{{ count }}</button>\n</template>\n```\n\n#### Phrase to recite\n\n`<script setup>` is sugar: top-level bindings go straight into the template, with no `return`, plus the macros `defineProps` / `defineEmits` / `defineExpose` / `defineModel`. It feels like an ordinary function component in React.\n\n#### React bridge\n\n`<script setup>` is approximately a function component: everything in the closure is immediately available in JSX or in the template. The macros are compiler magic (closer to Svelte). React has nothing like that: props are a function argument, and the imperative-ref API is `useImperativeHandle`, written by hand.\n\nFull answer: the Vue conspect → Q14\n"

    title: "How do you declare props and emits in `<script setup>` + TS? `withDefaults`"
    body: "#### Short answer\n\n**props** are data downward (parent → child).\n\n**emit** is an event upward (child → parent), instead of passing a callback as a prop.\n\nThe parent writes `<Child :title=\"name\" @save=\"onSave\" />`. The child calls `emit('save', id)`, and the parent's `onSave(id)` runs.\n\n#### Code example\n\n```\n<!-- ========== Child.vue ========== -->\n<script setup lang=\"ts\">\n// INPUT: props from the parent (like the component arguments in React)\nconst props = withDefaults(\n  defineProps<{\n    title: string\n    count?: number\n  }>(),\n  { count: 0 },\n)\n\n// OUTPUT: events upward (like onSave in React)\nconst emit = defineEmits<{\n  save: [id: number] // the parent receives a number\n}>()\n\nconst handleClick = () => {\n  // 1) the click was handled locally\n  // 2) an event plus a payload was sent upward\n  emit('save', props.count)\n}\n</script>\n\n<template>\n  <section>\n    <h2>{{ title }}</h2>\n    <p>count = {{ count }}</p>\n    <button type=\"button\" @click=\"handleClick\">Save</button>\n  </section>\n</template>\n\n<!-- ========== Parent.vue ========== -->\n<script setup lang=\"ts\">\nimport { ref } from 'vue'\nimport Child from './Child.vue'\n\nconst name = ref('Invoice')\nconst savedId = ref<number | null>(null)\n\n// this receives whatever the child passed to emit('save', ...)\nconst onSave = (id: number) => {\n  savedId.value = id\n  // then: an API call, the store, close the modal, and so on\n}\n</script>\n\n<template>\n  <!--\n    :title / :count  — props downward\n    @save            — listen for the child's emit('save')\n  -->\n  <Child\n    :title=\"name\"\n    :count=\"3\"\n    @save=\"onSave\"\n  />\n\n  <p v-if=\"savedId !== null\">Parent received id: {{ savedId }}</p>\n</template>\n\n<!--\nThe React equivalent of the same thing:\n\n<Child title={name} count={3} onSave={onSave} />\nfunction Child({ title, count, onSave }) {\n  return <button onClick={() => onSave(count)}>Save</button>\n}\n-->\n```\n\n#### Phrase to recite\n\n**props** = input (React props). **emit** = an output event (React `onSomething`). Data goes down, events go up. The parent's state changes only through emit, not by mutating props.\n\n#### React bridge\n\n| Vue | React |\n| --- | --- |\n| `defineProps<{ title: string }>()` | `type Props = { title: string }` plus the function argument |\n| `defineEmits` + `emit('save', id)` | `onSave?: (id: number) => void` plus the call |\n| `withDefaults` | default parameters / `defaultProps` (rare) |\n| A factory for array/object defaults | usually just `tags = []` in the destructure |\n\nIn React, callbacks are ordinary props. In Vue, events are a separate channel (`emit`), even though in the template you listen with `@save`.\n\nFull answer: the Vue conspect → Q17\n"

    title: "One-way data flow in Vue?"
    body: "#### Short answer\n\nProps go **down**, events go **up**. The child **does not mutate** props (in dev you get a warning). To change something, `emit`, and the parent updates the source of truth. For a two-way binding there is the `v-model` sugar, but inside it is still a prop plus an emit.\n\n#### Code example\n\n```\n<!-- Child -->\n<script setup lang=\"ts\">\ndefineProps<{ count: number }>()\nconst emit = defineEmits<{ inc: [] }>()\n</script>\n\n<template>\n  <button @click=\"emit('inc')\">{{ count }}</button>\n  <!-- bad: props.count++ -->\n</template>\n```\n\n#### Phrase to recite\n\nOne-way: props down, emit up. The child does not mutate props. `v-model` is only sugar over a prop plus `update:*`. It is not an exception to the rule.\n\n#### React bridge\n\nIt is the same idea: props down, callbacks up. `props.count++` is also a bad idea in React, and with primitives it often simply does not work. A controlled input is `value` plus `onChange`: the same one-way flow, plus a request to update.\n\nFull answer: the Vue conspect → Q18\n"

    title: "How does `v-model` work on a component? (`modelValue`, several v-models)"
    body: "#### Short answer\n\n`v-model` on a component is approximately `:modelValue` plus `@update:modelValue`. Several models: `v-model:title=\"title\"` becomes the `title` prop plus an `update:title` emit. From Vue 3.4 onward this is often written with `defineModel()`.\n\n#### Code example\n\n```\n<!-- Child without defineModel -->\n<script setup lang=\"ts\">\nconst props = defineProps<{ modelValue: string }>()\nconst emit = defineEmits<{ 'update:modelValue': [value: string] }>()\n\nconst onInput = (e: Event) => {\n  emit('update:modelValue', (e.target as HTMLInputElement).value)\n}\n</script>\n\n<template>\n  <input :value=\"modelValue\" @input=\"onInput\" />\n</template>\n```\n\n#### Phrase to recite\n\n`v-model` on a component is `modelValue` plus `update:modelValue`. `v-model:title` is the `title` prop plus `update:title`. In essence it is a controlled value/onChange pair, just shorter.\n\n#### React bridge\n\nIn React you write it by hand every time: `<Input value={text} onChange={e => setText(e.target.value)} />`. Vue `v-model` is syntactic sugar over that same controlled pair. Several v-models are several value/onChange pairs with different names.\n\nFull answer: the Vue conspect → Q19\n"

    title: "`defineModel` — what is it?"
    body: "#### Short answer\n\nA Vue 3.4+ macro. In one line it declares the prop and the emit for `v-model`. You read and write `model.value`, and the compiler sends `update:*` for you. Less boilerplate for controlled components.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\n// the default v-model\nconst model = defineModel<string>({ required: true })\n\n// a named one\nconst title = defineModel<string>('title', { default: '' })\n\n// usage\nmodel.value = 'hi' // ≈ emit('update:modelValue', 'hi')\n</script>\n\n<template>\n  <input v-model=\"model\" />\n  <input v-model=\"title\" />\n</template>\n```\n\n#### Phrase to recite\n\n`defineModel` (3.4+) is sugar: a ref-like API, with a prop plus `update:*` under the hood. I write `model.value = x` instead of a manual `emit('update:modelValue', x)`.\n\n#### React bridge\n\nThere is no macro equivalent. The closest thing is a custom hook:\n\n```\nfunction useModel(value: string, onChange: (v: string) => void) {\n  return [value, onChange] as const\n}\n```\n\nor a controlled input with `value` / `onChange`. `defineModel` specifically saves the Vue boilerplate of prop plus emit.\n\nFull answer: the Vue conspect → Q20\n"
