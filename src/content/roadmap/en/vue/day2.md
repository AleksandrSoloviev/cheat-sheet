    title: "What is a composable?"
    body: "#### Short answer\n\nA composable is a `useXxx()` function that encapsulates **stateful** logic on the Composition API (`ref`, `computed`, `watch`, lifecycle). It is the direct analogue of a **custom hook** in React. It is the main way to reuse logic in Vue 3 instead of mixins.\n\n#### Code example\n\n```\n// cheat sheet (not a full SFC)\n// composable\nexport function useToggle(initial = false) {\n  const on = ref(initial)\n  const toggle = () => { on.value = !on.value }\n  return { on, toggle }\n}\n```\n\n#### Phrase to recite\n\nA composable is Vue's custom hook: `useXxx` with refs, watch, and lifecycle. You call it in setup, it has cleanup, and the input is preferably a `MaybeRefOrGetter`.\n\n#### React bridge\n\n| Vue | React |\n| --- | --- |\n| `useXxx()` composable | `useXxx()` custom hook |\n| inside: `ref` / `watch` / `onMounted` | inside: `useState` / `useEffect` |\n| mixins → composables | HOCs / classes → hooks |\n\nFull answer: the Vue conspect → Q31\n"

    title: "What does a typical production-grade composable look like?"
    body: "#### Short answer\n\nA production-grade composable accepts a reactive or static input (`MaybeRefOrGetter`), tracks it inside with `toValue` / `watchEffect`, does cleanup, and returns refs and methods. It does not return raw mutable objects unless you actually need them.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nexport const useUser = (id: MaybeRefOrGetter<string>) => {\n  const user = ref<User | null>(null)\n  const error = ref<unknown>(null)\n  const loading = ref(false)\n\n  watch(() => toValue(id), async (newId, _old, onCleanup) => {\n    const ctrl = new AbortController()\n    onCleanup(() => ctrl.abort())\n    loading.value = true\n    try {\n      user.value = await fetchUser(newId, ctrl.signal)\n    } catch (e) {\n      if (!ctrl.signal.aborted) error.value = e\n    } finally {\n      loading.value = false\n    }\n  }, { immediate: true })\n\n  return { user, error, loading }\n}\n</script>\n```\n\n#### Phrase to recite\n\nA production-grade composable: `MaybeRefOrGetter` plus `toValue`, cleanup, and returned refs. For async work, abort in the watch `onCleanup`.\n\n#### React bridge\n\nThe structure is 1:1 with a hook:\n\n```\nfunction useMouse() {\n  const [x, setX] = useState(0)\n  useEffect(() => {\n    const onMove = (e) => setX(e.pageX)\n    window.addEventListener('mousemove', onMove)\n    return () => window.removeEventListener('mousemove', onMove)\n  }, [])\n  return { x }\n}\n```\n\n`MaybeRefOrGetter` means \"accept a value or a dependency\". It is close to what React often does with a `value` plus a separate `useEffect` that runs when that value changes.\n\nFull answer: the Vue conspect → Q32\n"

    title: "Composable vs Pinia vs provide/inject?"
    body: "#### Short answer\n\nThree different scales of sharing. A **composable** is reusable logic, often with local state per call. **Pinia** is a global domain store. **provide/inject** is a contract inside one branch of the tree (like Context), and it is not global.\n\n#### Code example\n\n```\n// cheat sheet (not a full SFC)\n// composable — logic per call\nconst { x, y } = useMouse()\n\n// Pinia — a global domain\nconst cart = useCartStore()\n\n// provide/inject — a contract for a branch of the tree\nprovide(formKey, formApi)\nconst formApi = inject(formKey)\n```\n\n#### Phrase to recite\n\nA composable is logic per call. Pinia is a global domain. provide/inject is Context for one branch. Do not mix the layers without a reason.\n\n#### React bridge\n\n| Vue | React |\n| --- | --- |\n| composable | custom hook |\n| Pinia | Zustand / Redux Toolkit |\n| provide/inject | `Context.Provider` / `useContext` |\n\nThe same rule applies: Context is not a global store for the whole app.\n\nFull answer: the Vue conspect → Q33\n"

    title: "What is Pinia? How is it better than Vuex?"
    body: "#### Short answer\n\nPinia is the **official** store for Vue 3. It is simpler than Vuex: there are no mutations, TypeScript is excellent, setup stores look like composables, and you get modularity without nested-modules hell. Knowing Vuex is useful for legacy code. New code should use Pinia.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nimport { defineStore } from 'pinia'\nimport { ref, computed } from 'vue'\n\nexport const useCounterStore = defineStore('counter', () => {\n  const count = ref(0)\n  const double = computed(() => count.value * 2)\n  const increment = () => { count.value++ }\n  return { count, double, increment }\n})\n// vs Vuex: no mutations; actions change state directly\n</script>\n```\n\n#### Phrase to recite\n\nPinia is the official Vue 3 store: no mutations, excellent TypeScript, and setup stores. Vuex is legacy.\n\n#### React bridge\n\nIt is closest to **Zustand** (a simple API) plus the role of **Redux Toolkit** (the official store a team standardizes on). Vuex mutations are an extra layer, like classic Redux before RTK.\n\nFull answer: the Vue conspect → Q34\n"

    title: "Setup store — an example"
    body: "#### Short answer\n\nA setup store looks like a composable inside `defineStore`: `ref` and `computed`, plus functions that act as actions, and a `return` of the public API. In a component, state is read through `storeToRefs`. Actions are used directly.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nexport const useCartStore = defineStore('cart', () => {\n  const items = ref<Item[]>([])\n  const total = computed(() =>\n    items.value.reduce((s, i) => s + i.price, 0)\n  )\n\n  function add(item: Item) {\n    items.value.push(item)\n  }\n\n  function clear() {\n    items.value = []\n  }\n\n  return { items, total, add, clear }\n})\n</script>\n```\n\n#### Phrase to recite\n\nA Pinia setup store is a composable inside `defineStore`: return refs, computed values, and actions. In the UI, use `storeToRefs` for state.\n\n#### React bridge\n\nIt is similar to Zustand:\n\n```\nconst useCart = create((set, get) => ({\n  items: [],\n  add: (item) => set({ items: [...get().items, item] }),\n}))\n```\n\nThe difference: in Pinia, mutating an array with `push` is normal, because of Vue reactivity.\n\nFull answer: the Vue conspect → Q35\n"

    title: "Why can't you just destructure a store?"
    body: "#### Short answer\n\n`const { count } = store` pulls the field off the reactive store. After that it is an ordinary number or value, and the UI will not update. State and getters need `storeToRefs(store)`. Actions can be destructured, because they are functions.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nconst store = useCounterStore()\n\n// bad — reactivity is lost\nconst { count } = store\ncount // no longer linked to the store\n\n// good\nconst { count } = storeToRefs(store)\ncount.value // a reactive ref\n\n// actions — fine\nconst { increment } = store\nincrement()\n</script>\n```\n\n#### Phrase to recite\n\nPinia state and getters only through `storeToRefs` or `store.field`. Actions can be destructured freely.\n\n#### React bridge\n\nIn Zustand, `const count = useStore(s => s.count)` is a subscription through a selector. In Redux it is `useSelector`. In Vue, \"just destructure the store object\" is not a selector, and that is the trap.\n\nFull answer: the Vue conspect → Q36\n"

    title: "Where do you not need Pinia?"
    body: "#### Short answer\n\nYou do not need it for local UI state: whether a modal is open, input text before submit, hover, or an ephemeral wizard on a single screen. Otherwise you get a god-store and extra coupling between features.\n\n#### Code example\n\n```\n// cheat sheet (not a full SFC)\n// NOT in Pinia\nconst isOpen = ref(false)          // modal UI\nconst draft = ref('')              // input draft\n\n// In Pinia\nconst user = useUserStore()        // session\nconst cart = useCartStore()        // a cart shared across pages\n```\n\n#### Phrase to recite\n\nPinia is for the domain and for state that crosses pages. Local UI and drafts are a `ref` in the component or in a composable.\n\n#### React bridge\n\nThe same idea as \"not everything belongs in Redux\": server state goes to React Query, local UI goes to `useState`, and a global domain goes to a store.\n\nFull answer: the Vue conspect → Q37\n"

    title: "Navigation guards?"
    body: "#### Short answer\n\nGuards are navigation hooks: global (`beforeEach`), on a route (`beforeEnter`), and inside a component (`onBeforeRouteLeave`, and others). The typical case is auth: if `meta.requiresAuth` and there is no session, redirect to login.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nrouter.beforeEach((to) => {\n  if (to.meta.requiresAuth && !isLoggedIn()) {\n    return { name: 'login', query: { redirect: to.fullPath } }\n  }\n})\n</script>\n```\n\n#### Phrase to recite\n\nGuards: `beforeEach` plus `meta.requiresAuth` means redirect. To leave a page, use `onBeforeRouteLeave`.\n\n#### React bridge\n\nAnalogues: React Router loaders and actions, Next middleware, or a manual redirect in `useEffect`. The idea is the same: centralize the auth check, and do not spread it across pages.\n\nFull answer: the Vue conspect → Q39\n"

    title: "Reactivity of `route.params`?"
    body: "#### Short answer\n\nGoing from `/users/1` to `/users/2` often does **not** unmount the component. Vue Router reuses the instance. `onMounted` will not run again. You need `watch(() => route.params.id, ...)` or `onBeforeRouteUpdate`.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nconst route = useRoute()\n\nwatch(\n  () => route.params.id,\n  (id) => { loadUser(String(id)) },\n  { immediate: true },\n)\n</script>\n```\n\n#### Phrase to recite\n\nA param change is not a remount. Watch `route.params.id` with `immediate`, or use `onBeforeRouteUpdate`.\n\n#### React bridge\n\nReact Router has the same story: one component type means the instance can stay. Load the data in `useEffect([id])`, not only on mount.\n\nFull answer: the Vue conspect → Q42\n"

    title: "Slots: default, named, and scoped?"
    body: "#### Short answer\n\n**Default** is `<slot />`, or content with no name. **Named** is `<slot name=\"header\" />` plus `#header` on the parent. **Scoped** is a slot that passes props, such as `:item=\"row\"`, and the parent destructures them with `#item=\"{ item }\"`. A scoped slot is approximately render props in React.\n\n#### Code example\n\n```\n<template>\n  <header>\n    <slot name=\"header\" />\n  </header>\n  <main>\n    <slot>Default fallback text</slot>\n  </main>\n  <ul>\n    <li v-for=\"row in rows\" :key=\"row.id\">\n      <slot name=\"item\" :item=\"row\" :index=\"row.id\">\n        {{ row.name }}\n      </slot>\n    </li>\n  </ul>\n</template>\n```\n\n#### Phrase to recite\n\nDefault and named slots are where the parent's markup goes. A scoped slot is the child passing data into the slot so the parent can draw the UI. That is render props, the Vue way.\n\n#### React bridge\n\n| Vue | React |\n| --- | --- |\n| default slot | `children` |\n| named slot | `header={...}` / a `<HeaderSlot />` prop |\n| scoped slot | a render prop `renderItem={(item) => ...}`, or `children(item)` |\n\n```\n<List renderItem={(item) => <strong>{item.name}</strong>} />\n```\n\nFull answer: the Vue conspect → Q25\n"

    title: "Fetch in `onMounted` vs `watch`?"
    body: "#### Short answer\n\nData that depends on `route.params` or props belongs in **`watch` with `immediate: true`** (or `watchEffect`), so you react to an id change **without** a remount. A one-time fetch when the screen opens, with no reactive dependency, belongs in `onMounted`. In Nuxt, use `useAsyncData` or `useFetch` (SSR plus a cache key).\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nconst route = useRoute()\nconst user = ref<User | null>(null)\nconst error = ref<Error | null>(null)\n\nwatch(\n  () => route.params.id,\n  async (id, _prev, onCleanup) => {\n    const ac = new AbortController()\n    onCleanup(() => ac.abort()) // cancel on a new id or on unmount\n\n    try {\n      user.value = await fetchUser(String(id), ac.signal)\n      error.value = null\n    } catch (e) {\n      if ((e as Error).name === 'AbortError') return\n      error.value = e as Error\n    }\n  },\n  { immediate: true },\n)\n</script>\n```\n\n#### Phrase to recite\n\nA fetch that depends on an `id` or on the route is a `watch` with `immediate: true` and an abort in `onCleanup`. A pure one-shot with no dependency is `onMounted`. In React both cases are one `useEffect([id])`.\n\n#### React bridge\n\n```\nuseEffect(() => {\n  let cancelled = false\n  fetchUser(id).then(...)\n  return () => { cancelled = true }\n}, [id])\n```\n\nOne `useEffect` with `[id]` covers both mount and an id change. In Vue that split is explicit: \"mount only\" versus `watch` plus `immediate`. It is a common interview nuance about the router reusing the component.\n\nFull answer: the Vue conspect → Q30\n"
