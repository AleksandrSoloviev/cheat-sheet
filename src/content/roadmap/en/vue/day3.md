    title: "What is the main philosophical difference?"
    body: "#### Short answer\n\nVue: reactive data plus templates (the compiler optimizes them), and \"official batteries included.\" React: UI = f(state), an immutable rerender world, JSX, and a huge ecosystem. Both are component-based; composables ≈ hooks.\n\n#### Code example\n\n```\n// cheat sheet (not a full SFC)\n// React: UI = f(state) — setState re-renders the function\nsetCount(c => c + 1)\n\n// Vue: the data calls its subscribers\nconst count = ref(0)\ncount.value++ // only the subscribers that read count update\n```\n\n#### Phrase to recite\n\nVue = reactivity + templates + batteries; React = UI = f(state) + JSX + ecosystem; both reuse logic in a hooks-like way.\n\n#### React bridge\n\nSeven years in React is a strength: you can compare the two deliberately, not religiously.\n\nFull answer: the Vue conspect → Q61\n"

    title: "How do you debug \"the UI is not updating\"?"
    body: "#### Short answer\n\nChecklist: is it a `ref` or `reactive` at all? Did destructuring lose reactivity? Did you mutate deep inside a `shallowRef`? Is the router reusing the component with no watch? Did `v-if` destroy the state? Does DevTools show the state change?\n\n#### Code example\n\n```\n// cheat sheet (not a full SFC)\n// Checklist: \"the UI is not updating\"\nconst { count } = store          // ❌ lost reactivity\nconst { count } = storeToRefs(store) // ✅\n\nlist.value.push(item)            // ❌ if it is a shallowRef\nlist.value = [...list.value, item]   // ✅\n\n// route /users/1 → /users/2 with no remount\nwatch(() => route.params.id, load, { immediate: true })\n```\n\n#### Phrase to recite\n\nThe UI is not updating: DevTools, then reactivity, destructuring, shallow, route reuse, and `v-if`. Walk the checklist in that order.\n\n#### React bridge\n\nReact: \"is the state a new reference?\", memo blocks the update, a wrong key, an effect with missing deps.\n\nFull answer: the Vue conspect → Q71\n"

    title: "What are the main breaking changes from Vue 2 to Vue 3?"
    body: "#### Short answer\n\nThe main ones: reactivity on Proxy, `createApp` instead of `new Vue`, filters removed, `$listeners` merged into `$attrs`, fragments allowed, no IE11, the ecosystem moves from Vuex to Pinia, and the event bus goes away.\n\n#### Code example\n\n```\n// cheat sheet (not a full SFC)\n// Vue 2                          → Vue 3\n// new Vue({...}).$mount()        → createApp(App).mount('#app')\n// this.$set(obj, 'a', 1)         → obj.a = 1 (Proxy)\n// filters                        → computed / methods\n// value + input (v-model)        → modelValue + update:modelValue\n// Vuex mutations                 → Pinia actions\n```\n\n#### Phrase to recite\n\nVue 2→3: Proxy, createApp, no filters, a new v-model, $attrs instead of $listeners, Pinia instead of Vuex.\n\n#### React bridge\n\nLike a major migration from React 17→18 / class→hooks: breaking APIs plus a new mindset, and legacy stays nearby for a long time.\n\nFull answer: the Vue conspect → Q58\n"
  - id: "22"
    title: "`v-if` vs `v-show`?"
    body: "#### Short answer\n\n`v-if` is a conditional **mount/unmount** (more expensive to toggle, cheaper while hidden, because it is not in the DOM). `v-show` is only CSS `display`; the node is always in the DOM. Frequent toggling points to `v-show`. A rare toggle, a heavy tree, or a need for a full teardown points to `v-if`.\n\n#### Code example\n\n```\n<template>\n<!-- v-if: mount/unmount -->\n<div v-if=\"isAdmin\">Admin panel</div>\n\n<!-- v-show: CSS display, the DOM node stays -->\n<div v-show=\"isOpen\">Dropdown</div>\n\n<!-- Frequent toggling → v-show; rare/heavy → v-if -->\n</template>\n```\n\n#### Phrase to recite\n\n`v-if` mounts and destroys. `v-show` only hides through CSS. Frequent flicker calls for `v-show`. Something rare and heavy calls for `v-if`.\n\n#### React bridge\n\n`{cond && <X />}` or a ternary is roughly `v-if`. `style={{ display: cond ? 'block' : 'none' }}` is roughly `v-show`. React has no separate directive. The tradeoff is the same: mount versus hiding with CSS.\n\nFull answer: the Vue conspect → Q22\n"
  - id: "23"
    title: "`v-for` and `key`; the `v-if` + `v-for` pitfall"
    body: "#### Short answer\n\nAlways use a stable unique `:key` (the entity id, not the index, when the list is reordered or filtered). A `key` on a component forces a remount when it changes. **`v-if` and `v-for` on the same element is a bad idea:** in Vue 3, `v-if` has higher priority, which gets confusing. Filter through a `computed`.\n\n#### Code example\n\n```\n<template>\n<!-- key = a stable id -->\n<li v-for=\"user in users\" :key=\"user.id\">{{ user.name }}</li>\n\n<!-- Bad: v-if + v-for on the same node -->\n<!-- <div v-for=\"u in users\" v-if=\"u.active\"> -->\n\n<!-- Good: filter in a computed -->\n<li v-for=\"u in activeUsers\" :key=\"u.id\">{{ u.name }}</li>\n<!-- const activeUsers = computed(() => users.value.filter(u => u.active)) -->\n</template>\n```\n\n#### Phrase to recite\n\nUse a stable `key` by id, not by index, when the list mutates. I keep `v-if` and `v-for` off the same node and filter in a `computed`, because in Vue 3 `v-if` has higher priority.\n\n#### React bridge\n\nThe reconciliation semantics are the same: `key` inside `.map()`. Index-as-key is the same anti-pattern. Filtering the list before map is like a computed before v-for. React has no directive conflict between v-if and v-for. You simply do not write that kind of meaningless code in one expression.\n\nFull answer: the Vue conspect → Q23\n"
