    title: "`shallowRef` / `shallowReactive` — why?"
    body: "#### Short answer\n\nThis is shallow reactivity. `shallowRef` tracks only a replacement of `.value`. `shallowReactive` tracks only the first level of fields. Nested values are not inside a Proxy. You need them for large data, immutable updates, and third-party libraries where a deep Proxy gets in the way or costs too much.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nconst list = shallowRef<Item[]>(hugeArray)\n\n// ❌ a mutation inside does NOT trigger the UI\nlist.value.push(newItem)\n\n// ✅ the trigger is a new reference on .value\nlist.value = [...list.value, newItem]\n// or\nlist.value = list.value.concat(newItem)\ntriggerRef(list) // rare: force an update if you mutated in place on purpose\n</script>\n```\n\n#### Phrase to recite\n\n`shallowRef` and `shallowReactive` are reactive only at the root. For large structures and third-party libraries I update with a new reference, with no deep Proxy. Nested mutations will not wake the UI on their own.\n\n#### React bridge\n\n| What | Vue shallow* | React |\n| --- | --- | --- |\n| Model | opt-in shallow | state always updates through a new root reference |\n| Update | a new reference for `.value` or a field | setState(newRef) |\n| Deep mutate | does not trigger (same as in React) | does not trigger |\n| Deep reactive | `ref` / `reactive` by default | not built in |\n\nTo a React developer, `shallowRef` often feels like `useState`: it triggers only on a new reference. Deep `reactive` is something React does not have.\n\nFull answer: the Vue conspect → Q7\n"

    title: "What does `nextTick` do?"
    body: "#### Short answer\n\nVue batches DOM updates asynchronously. `await nextTick()` waits until the DOM applies the current reactive changes. You need it when, right after a state mutation, you read or touch the DOM (`focus`, `scrollHeight`).\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\nconst box = ref<HTMLElement | null>(null)\nconst open = ref(false)\n\nconst handleOpen = async () => {\n  open.value = true\n  // the DOM may not contain the opened block yet\n  await nextTick()\n  // v-if has rendered the element now\n  box.value?.focus()\n  console.log(box.value?.scrollHeight)\n}\n</script>\n```\n\n#### Phrase to recite\n\n`nextTick` waits until Vue flushes the batched DOM updates. After `open.value = true` I `await nextTick()`, and only then `focus` or `scrollHeight`.\n\n#### React bridge\n\n| Vue | React |\n| --- | --- |\n| batched updates (by default) | batched updates (React 18+) |\n| `await nextTick()` | `useEffect` after commit; `flushSync` if you need a sync DOM; sometimes `requestAnimationFrame` |\n| focus after showing the node | `useEffect` plus a ref, or a callback ref |\n\nIn React, \"wait for the DOM\" usually means an effect after paint or commit. In Vue, an explicit `nextTick` in the same async flow, right after the state change, is the usual pattern.\n\nFull answer: the Vue conspect → Q8\n"

    title: "How does Vue 3 implement reactivity? (Proxy)"
    body: "#### Short answer\n\n`reactive()` wraps an object in a `Proxy`. On `get` it calls `track` (who read the field). On `set` and `deleteProperty` it calls `trigger` (notify subscribers). `ref` is a wrapper with a reactive `.value`. Objects inside it become reactive too. Vue 2 did this with `Object.defineProperty`, which is where the old limitations come from.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\n// the idea, not a line-for-line copy of the source\nfunction reactive(target) {\n  return new Proxy(target, {\n    get(obj, key, receiver) {\n      track(obj, key)          // the active effect subscribed\n      const value = Reflect.get(obj, key, receiver)\n      // nested objects are proxied too (deep)\n      return isObject(value) ? reactive(value) : value\n    },\n    set(obj, key, value, receiver) {\n      const result = Reflect.set(obj, key, value, receiver)\n      trigger(obj, key)        // rerun computed / watch / render\n      return result\n    },\n    deleteProperty(obj, key) {\n      const result = Reflect.deleteProperty(obj, key)\n      trigger(obj, key)\n      return result\n    },\n  })\n}\n</script>\n```\n\n#### Phrase to recite\n\nVue 3 is a Proxy: get does track, set and delete do trigger. That is how `reactive` and `ref` work, plus Map and Set support. Vue 2 used `defineProperty`, with gaps on new keys, which is why `Vue.set` existed.\n\n#### React bridge\n\n| What | Vue | React |\n| --- | --- | --- |\n| Watching the data | a Proxy on the user's state | No. It compares props and state by reference after setState |\n| Who collects deps | runtime track on read | you (deps) / the compiler (React Compiler) |\n| UI engine | reactivity plus a VDOM patch | Fiber reconciliation |\n\nReact does not wrap your object in a Proxy. Vue does, so mutations show up on their own.\n\nFull answer: the Vue conspect → Q9\n"

It is roughly a React portal. **KeepAlive** caches instances of dynamic children (`include` / `exclude` / `max`), with the `onActivated` and `onDeactivated` hooks. **Suspense** is a fallback while async setup or an async component is loading.\n\n#### Code example\n\n```\n<Suspense>\n  <RouterView />\n  <template #fallback>\n    <Spinner />\n  </template>\n</Suspense>\n```\n\n#### Phrase to recite\n\nTeleport is a portal into another DOM node. KeepAlive is an instance cache with activated and deactivated. Suspense is a fallback for async setup or an async component. KeepAlive out of the box is stronger than what React ships.\n\n#### React bridge\n\n| Vue | React |\n| --- | --- |\n| Teleport | `createPortal(..., document.body)` |\n| KeepAlive | no 1:1 match; react-router outlets plus a manual cache or a library |\n| Suspense | React.Suspense (data and code) — a similar idea |\n\nFull answer: the Vue conspect → Q27\n"

    body: "#### Short answer\n\n`useAsyncData` is the primitive: a key plus an async factory. `useFetch` is sugar over it plus `$fetch` (a URL and options). A unique key is critical for SSR and hydration.\n\n#### React bridge\n\nNext: fetch on the server, or `getServerSideProps`. On the client: SWR or React Query. Cache keys are the same mental model.\n\nFull answer: the Vue conspect → Q52\n"

    title: "What is a hydration mismatch?"
    body: "#### Short answer\n\nSSR sent HTML, and during hydration the client rendered something else, which shows up as a warning or a bug. Causes: `Date.now()`, `random`, `window` in setup, or different data or locale. The fix: the same source of data, `ClientOnly`, and browser-only work in `onMounted`.\n\n#### Code example\n\n```\n<script setup lang=\"ts\">\n// Bad — different HTML on the server and the client\nconst now = Date.now()        // in the template\nconst w = window.innerWidth   // in setup during SSR\n\n// Good\nonMounted(() => { width.value = window.innerWidth })\n// or <ClientOnly>...</ClientOnly>\n</script>\n```\n\n#### Phrase to recite\n\nA mismatch means the server HTML is not the client HTML. Take random and window out of the first render, and align the data.\n\n#### React bridge\n\nThe same hydration warning in React SSR and in Next. The idea is the same.\n\nFull answer: the Vue conspect → Q53\n"

    title: "Auth flow, end to end?"
    body: "#### Short answer\n\nLogin, then a token (an httpOnly cookie is better than localStorage alone), then Pinia `user`, then a router `beforeEach` that checks `meta.requiresAuth`, then an interceptor on 401 that logs out and redirects. For SSR: the cookie plus server middleware.\n\n#### Code example\n\n```\n// cheat sheet (not a full SFC)\n// login → cookie/session → Pinia user → guard\nrouter.beforeEach((to) => {\n  const user = useUserStore()\n  if (to.meta.requiresAuth && !user.isLoggedIn) {\n    return { name: 'login', query: { redirect: to.fullPath } }\n  }\n})\n\n// axios interceptor: 401 → logout + redirect\n```\n\n#### Phrase to recite\n\nAuth: a cookie or session, then Pinia user, then `beforeEach` on `meta.requiresAuth`, then a 401 interceptor, then logout.\n\n#### React bridge\n\nSame as in React: an auth context or store, protected routes, and axios interceptors. On SSR, NextAuth or middleware.\n\nFull answer: the Vue conspect → Q70\n"
