    topic: "Управление состоянием"
    title: "Какие недостатки у Context API? Почему вместо него выбрал Redux?"
    body: |
      #### Короткий ответ

      Context API передаёт значение вниз по дереву. Подписчик читает его через `useContext`. Недостаток в том, как устроена подписка: новое значение контекста перерисовывает всех, кто этот контекст читает. Если в одном объекте лежат пользователь и список задач, смена задач перерисует и компонент, которому нужно только имя.

      Второе место, где это ломается, — новое значение на каждом рендере провайдера. Объект, собранный прямо в JSX, каждый раз другой по ссылке, и подписчики обновляются снова, даже если поля те же.

      У Context API нет встроенного журнала действий, middleware и отдельного места для асинхронного потока. Редкое значение вроде темы он закрывает спокойно. Redux выбирают, когда одни и те же данные читают много компонентов по частям: `useSelector` подписывает компонент на результат селектора, обновление идёт действием через редюсер, а побочный эффект живёт в middleware.

      #### Пример кода

      ```jsx
      const AppContext = createContext(null);

      function UserName() {
        const value = useContext(AppContext);
        return <span>{value.user.name}</span>;
      }

      function App() {
        const user = { name: 'Ada' };
        const tasks = [{ id: '1' }];

        return (
          <AppContext.Provider value={{ user, tasks }}>
            <UserName />
          </AppContext.Provider>
        );
      }
      ```

      ```jsx
      const name = useSelector((state) => state.user.name);
      ```

      В первом фрагменте `value` — новый объект на каждом рендере `App`, поэтому `UserName` обновляется и тогда, когда меняются только `tasks`. Селектор во втором фрагменте возвращает имя: компонент, который читает только его, не подписан на остальные поля store.

      #### Фраза на автомате

      Context API я беру для редких значений вроде темы. Его слабое место — подписка на всё значение: любой новый объект контекста перерисовывает всех потребителей, даже если компоненту нужно одно поле. Для списков, которые читают много экранов, я выбираю Redux: срез забираю через `useSelector`, а обновление проходит действием и редюсером.

    title: "Знаешь Redux Saga?"
    body: |
      #### Короткий ответ

      Да. Redux Saga — middleware для побочных эффектов. Сага — генератор. Она перехватывает действие, выполняет эффект и отправляет следующее действие в store. Типичная связка: `takeEvery` или `takeLatest` слушает тип действия, `call` вызывает API, `put` делает `dispatch` результата.

      Редюсер при этом остаётся чистой функцией и сам запрос не выполняет. Сагу подключают к store как middleware, рядом с остальной цепочкой.

      Это уровень устройства, а не история конкретного внедрения. Если в проекте ты пользовался thunk или listener из Redux Toolkit, так и говоришь, и показываешь, что Saga тебе знакома по этой схеме.

      #### Пример кода

      ```javascript
      function* loadUsers(action) {
        const users = yield call(fetchUsers, action.payload);
        yield put({ type: 'users/loaded', payload: users });
      }

      function* usersSaga() {
        yield takeEvery('users/fetch', loadUsers);
      }
      ```

      #### Фраза на автомате

      Redux Saga я знаю как middleware для побочных эффектов. Сага — генератор: `takeEvery` слушает действие, `call` ходит в API, `put` кладёт результат обратно в store. Редюсер остаётся чистым, запрос живёт в саге.
  - id: suryateja-digibank.2e
    label: "2e"
    topic: "Управление состоянием"
    title: "Объясни путь от отправки действия до данных обратно."
    body: |
      #### Короткий ответ

      Путь такой. Компонент вызывает `dispatch` с действием: тип и, если нужно, payload. Store проводит это действие через цепочку middleware. Thunk или Redux Saga на этом шаге может вызвать API. Когда ответ есть, middleware отправляет следующее действие, уже с данными или с ошибкой.

      Дальше действие доходит до редюсера. Редюсер — чистая функция: прежний state и действие, на выходе следующий state. Запрос внутри редюсера не делают. Store сохраняет новый state и сообщает подписчикам. `useSelector` возвращает новый срез, и компонент рисует его.

      Обратно в компонент данные попадают не как возвращаемое значение `dispatch`, а как новый state, прочитанный селектором.

      #### Пример кода

      ```javascript
      dispatch({ type: 'users/fetch' });

      function usersReducer(state = { items: [] }, action) {
        if (action.type === 'users/loaded') {
          return { items: action.payload };
        }

        return state;
      }
      ```

      ```jsx
      const users = useSelector((state) => state.users.items);
      ```

      Первое действие стартует загрузку в middleware. Действие `users/loaded` уже несёт список, редюсер кладёт его в state, селектор отдаёт список компоненту.

      #### Фраза на автомате

      Я делаю `dispatch` действия. Middleware может сходить в API и отправить следующее действие уже с данными. Редюсер чисто считает следующий state, store сохраняет его, а компонент забирает срез через `useSelector`. Назад данные приходят как новый state, а не как return у `dispatch`.

    topic: "Управление состоянием"
    title: "Сценарий. Вызвать API, получить список пользователей или задач, положить в store Redux и использовать в нескольких компонентах. Как бы ты это устроил в паттерне Redux/Flux?"
    body: |
      #### Короткий ответ

      В Redux/Flux поток односторонний. Для списка пользователей или задач я завожу один срез store: сами элементы и статус загрузки. Сторона вида отправляет действие «загрузить». Побочный эффект, thunk или сага, вызывает API и следом отправляет действие с массивом. Редюсер заменяет элементы в срезе. Несколько компонентов читают один и тот же селектор и поэтому видят один список.

      Для задач структура та же: другой ключ state, те же роли у действия, эффекта, редюсера и селектора. Компоненты список не кэшируют у себя в `useState`, иначе экраны разъедутся.

      #### Пример кода

      ```jsx
      function usersReducer(state = { items: [], status: 'idle' }, action) {
        switch (action.type) {
          case 'users/loading':
            return { ...state, status: 'loading' };
          case 'users/loaded':
            return { items: action.payload, status: 'ready' };
          default:
            return state;
        }
      }

      const fetchUsers = () => async (dispatch) => {
        dispatch({ type: 'users/loading' });
        const response = await fetch('/api/users');
        const users = await response.json();
        dispatch({ type: 'users/loaded', payload: users });
      };

      const selectUsers = (state) => state.users.items;

      function UserList() {
        const users = useSelector(selectUsers);
        return <p>{users.length}</p>;
      }

      function UserCount() {
        const users = useSelector(selectUsers);
        return <p>{users.length}</p>;
      }
      ```

      `UserList` и `UserCount` подписаны на один селектор. После `users/loaded` оба видят один и тот же массив. Срез задач собирается теми же четырьмя ролями.

      #### Фраза на автомате

      Список пользователей или задач я кладу в один срез Redux. Компонент диспатчит загрузку, thunk или сага вызывает API и диспатчит данные, редюсер записывает массив. Несколько компонентов читают один селектор, поэтому список у них общий. Для задач я повторяю ту же схему Flux: действие, эффект, редюсер, селектор.

  - id: suryateja-digibank.4b
    label: "4b"
    topic: "Debounce (лайвкодинг)"
    title: "Лайвкодинг: напиши кастомный хук useDebounce, который принимает задержку. Для поля поиска вызывай API только через 500 мс после того, как пользователь перестал печатать."
    body: |
      #### Короткий ответ

      Хук `useDebounce` принимает значение и задержку и возвращает значение, которое обновляется только после паузы. Внутри `useEffect` ставит `setTimeout`. В cleanup эффекта вызывается `clearTimeout`, поэтому быстрый ввод не копит несколько срабатываний.

      Поле поиска хранит текст в своём state и вызывает хук с задержкой 500. Второй `useEffect` зависит уже от отложенного текста и только тогда вызывает `/api/users`. Пока человек печатает, меняется сырой текст, а запрос ждёт 500 мс тишины.

      Пример ниже — разбор условия. Это рабочий минимальный вариант на формулировку вопроса, а не расшифровка чужого экрана.

      #### Пример кода

      ```jsx
      import { useEffect, useState } from 'react';

      function useDebounce(value, delay) {
        const [debouncedValue, setDebouncedValue] = useState(value);

        useEffect(() => {
          const timerId = setTimeout(() => {
            setDebouncedValue(value);
          }, delay);

          return () => {
            clearTimeout(timerId);
          };
        }, [value, delay]);

        return debouncedValue;
      }

      function UserSearch() {
        const [query, setQuery] = useState('');
        const debouncedQuery = useDebounce(query, 500);

        useEffect(() => {
          if (debouncedQuery === '') {
            return;
          }

          const controller = new AbortController();

          fetch(`/api/users?q=${encodeURIComponent(debouncedQuery)}`, {
            signal: controller.signal,
          });

          return () => {
            controller.abort();
          };
        }, [debouncedQuery]);

        return (
          <input
            value={query}
            onChange={(event) => setQuery(event.target.value)}
          />
        );
      }
      ```

      #### Фраза на автомате

      `useDebounce` принимает значение и задержку. В эффекте я ставлю таймер и в cleanup вызываю `clearTimeout`. Для поиска передаю 500 мс. Запрос зависит от отложенного значения, поэтому он уходит один раз, когда пользователь перестал печатать.
  - id: suryateja-digibank.4c
    label: "4c"
    topic: "Debounce (лайвкодинг)"
    title: "Зачем внутри хука вызывается clearTimeout?"
    body: |
      #### Короткий ответ

      `clearTimeout` отменяет предыдущий таймер. Каждое изменение `value` заново запускает эффект: сначала cleanup прошлого запуска, потом новый `setTimeout`. Без отмены каждый ввод оставил бы свой таймер, и через 500 мс сработали бы все, включая промежуточные строки.

      Тот же cleanup выполняется при размонтировании. Тогда поздний таймер не вызовет `setDebouncedValue` на компоненте, которого уже нет.

      #### Пример кода

      ```jsx
      useEffect(() => {
        const timerId = setTimeout(() => {
          setDebouncedValue(value);
        }, delay);

        return () => {
          clearTimeout(timerId);
        };
      }, [value, delay]);
      ```

      #### Фраза на автомате

      `clearTimeout` я вызываю, чтобы сбросить таймер прошлого ввода. Пока человек печатает, старые срабатывания отменяются, и отложенное значение обновляется один раз после паузы. При размонтировании cleanup тоже гасит таймер.
  - id: suryateja-digibank.4d
    label: "4d"
    topic: "Debounce (лайвкодинг)"
    title: "useEffect выполняется при каждом изменении value?"
    body: |
      #### Короткий ответ

      Да, если `value` стоит в массиве зависимостей. После рендера, в котором `value` изменился, React сначала вызывает cleanup прошлого эффекта, потом тело эффекта заново. В debounce это как раз ставит новый таймер на новое значение.

      Тело эффекта и колбэк таймера — разные моменты. Эффект бежит на каждое изменение `value`. `setDebouncedValue` внутри таймера выполняется только если этот таймер дожил до конца задержки и его не снял `clearTimeout`.

      Пустой массив зависимостей оставил бы эффект на один запуск после монтирования. Без массива эффект шёл бы после каждого рендера компонента.

      #### Пример кода

      ```jsx
      useEffect(() => {
        const timerId = setTimeout(() => {
          setDebouncedValue(value);
        }, delay);

        return () => {
          clearTimeout(timerId);
        };
      }, [value, delay]);
      ```

    body: |
      #### Короткий ответ

      Да. `Promise.all` принимает список промисов, запускает ожидание всех и возвращает массив результатов в том же порядке. Если один промис отклоняется, `Promise.all` отклоняется тоже, и результаты остальных в это присваивание не попадают. Остальные запросы в сети при этом сами не отменяются.

На выходе массив той же длины: у успеха `status` равен `fulfilled` и есть `value`, у отказа `status` равен `rejected` и есть `reason`. Его берут, когда нужны оба исхода, а не только случай «все удались».

      #### Пример кода

      ```javascript
      async function readJson(url) {
        const response = await fetch(url);

        if (!response.ok) {
          throw new Error(String(response.status));
        }

        return response.json();
      }

      const [users, tasks] = await Promise.all([
        readJson('/api/users'),
        readJson('/api/tasks'),
      ]);

      const results = await Promise.allSettled([
        readJson('/api/users'),
        readJson('/api/tasks'),
      ]);
      ```

      #### Фраза на автомате

      `Promise.all` я использую, когда нужны все ответы: один отказ отклоняет весь `Promise.all`. `Promise.allSettled` я использую, когда хочу дождаться каждого вызова. Он возвращает статус `fulfilled` или `rejected` по каждому промису и сам не падает из-за одного отказа.

      Когда модуль не загрузился, `import()` отклоняется ещё до нормального рендера remote. Этот отказ перехватывают на промисе загрузки и подставляют компонент запасного экрана. Слот остаётся занятым этим экраном, базовое приложение не разбирается. Повтор можно повесить на кнопку, которая снова вызывает загрузку того же модуля.

      `Suspense` с текстом «Loading» — экран ожидания чанка, а не запасной экран ошибки. Запасной экран показывается, когда этот микрофронтенд уже не удалось ни загрузить, ни отрисовать.

      #### Пример кода

      ```jsx
      import { lazy, Suspense } from 'react';

      const Tasks = lazy(() =>
        import('tasks/Tasks').catch(() => ({
          default: function TasksFallback() {
            return <section>This section is unavailable.</section>;
          },
        })),
      );

      function Shell() {
        return (
          <main>
            <Suspense fallback={<p>Loading</p>}>
              <Tasks />
            </Suspense>
            <UsersRemote />
          </main>
        );
      }
      ```

      #### Фраза на автомате

      Кроме error boundaries я ставлю запасной экран в слот этого микрофронтенда. Если `import()` remote упал, `catch` возвращает компонент-замену, и на месте раздела видно, что он недоступен. Оболочка и остальные микрофронтенды остаются рабочими. Это отдельный экран ошибки, не текст ожидания у `Suspense`.
