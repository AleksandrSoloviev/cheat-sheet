  - id: "sree-wealth.2a"
    label: "2a"
    topic: "Virtual DOM"
    title: "Объясни Virtual DOM и как он работает в React."
    body: |
      #### Короткий ответ

      Virtual DOM в React — это описание интерфейса в памяти, а не узлы браузера. Компонент возвращает элементы: тип, props и дети. Это обычные объекты. Когда меняется state, React вызывает компонент снова и получает новое дерево.

      Reconciliation сравнивает новое дерево с предыдущим и решает, какие узлы настоящего DOM создать, обновить или удалить. Всё дерево браузера заново не собирается. Дорогая часть — запись в документ, а не создание объектов.

      В текущем React это дерево хранится как fiber. У узла есть тип, props, state и связи с ребёнком и соседом. На собеседовании Virtual DOM — это дерево и diff по нему. Ты описываешь UI от state, React применяет патч к настоящему DOM.

      #### Пример кода

      ```tsx
      const nextTree = {
        type: 'div',
        props: {
          children: [{ type: 'button', props: { children: 'Save' } }],
        },
      };

      // React diffs nextTree against the previous tree, then patches the real DOM.
      ```

      #### Фраза на автомате

      Virtual DOM — дерево React-элементов в памяти. После обновления state компонент возвращает новое дерево, reconciliation сравнивает его с прошлым и меняет только нужные узлы настоящего DOM. В React это fiber: тип, props и state на узле.
  - id: "sree-wealth.2b"
    label: "2b"
    topic: "Virtual DOM"
    title: "Сценарий. Компонент A возвращает div и рендерит внутри него компонент B. В A есть state, который меняется с false на true, и из-за этого div становится p. Что происходит с компонентом B: он перерисовывается или размонтируется и монтируется заново?"
    body: |
      #### Короткий ответ

      Component B размонтируется и монтируется заново. State этого экземпляра пропадает.

      В A state переходит с false на true, и элемент в той же позиции меняется с `div` на `p`. У fiber тип становится другим: host-компонент `div` и host-компонент `p` — разные типы. Reconciliation идёт по типу и по позиции. Позиция та же, единственный ребёнок на этом месте, а тип не совпал. React удаляет старый fiber вместе со всем поддеревом и создаёт новый fiber для `p`.

      Component B лежит внутри этого узла, поэтому его fiber тоже уничтожается. Новый B монтируется с начальным state. Локальный счётчик или введённый текст возвращаются к стартовым значениям. Это смена экземпляра, а не обновление того же B.

      Если тип родителя остаётся `div`, а меняются только props или текст, тип и позиция B совпадают. Тогда fiber B сохраняется, state жив, и B перерисовывается.

      Стабильный `key` на B это не удерживает. Ключ сопоставляет соседей внутри одного родителя. Родительский host-узел удалён, и дети удаляются вместе с ним. До сравнения ключей B дело не доходит.

      #### Пример кода

      ```tsx
      import { useState } from 'react';

      function ComponentB() {
        const [count, setCount] = useState(0);

        return (
          <span onClick={() => setCount((value) => value + 1)}>{count}</span>
        );
      }

      function ComponentA() {
        const [asParagraph, setAsParagraph] = useState(false);
        const Parent = asParagraph ? 'p' : 'div';

        return (
          <>
            <button type="button" onClick={() => setAsParagraph(true)}>
              Switch
            </button>
            <Parent>
              <ComponentB />
            </Parent>
          </>
        );
      }
      ```

      #### Фраза на автомате

      Смена `div` на `p` меняет тип fiber в той же позиции. Reconciliation сравнивает тип и позицию: тип не совпал, старое поддерево размонтируется, Component B монтируется заново, state пропадает. Тот же тип в той же позиции обновился бы на месте и сохранил state. Key на B родителя с новым типом не переживает.
  - id: "sree-wealth.3a"
    label: "3a"
    topic: "Хуки: useEffect и useLayoutEffect"
    title: "В чём разница между useEffect и useLayoutEffect?"
    body: |
      #### Короткий ответ

      Оба хука запускают эффект после коммита и принимают массив зависимостей и cleanup. Разница во времени относительно отрисовки кадра.

      useLayoutEffect выполняется после того, как React записал DOM, и до того, как браузер нарисовал кадр. Он блокирует paint. Сюда кладут чтение геометрии и синхронную поправку, которую пользователь не должен увидеть промежуточным кадром.

      useEffect выполняется после paint. Сюда кладут запрос, подписку, лог и запись в document.title. Медленную работу в useLayoutEffect не ставят: кадр ждёт, пока эффект закончится.

      На сервере геометрии нет, поэтому useLayoutEffect — клиентский хук. В серверном рендере React предупреждает, если он попал в проход, где layout ещё не существует.

      #### Пример кода

      ```tsx
      import { useEffect, useLayoutEffect, useRef } from 'react';

      function Box() {
        const ref = useRef(null);

        useLayoutEffect(() => {
          ref.current.style.opacity = '1';
        }, []);

        useEffect(() => {
          document.title = 'ready';
        }, []);

        return <div ref={ref} style={{ opacity: 0 }} />;
      }
      ```

      #### Фраза на автомате

      useLayoutEffect бежит после записи DOM и до paint, поэтому им измеряют layout и правят его без мигания. useEffect бежит после paint: запросы, подписки, логи. Зависимости и cleanup у них одинаковые. Тяжёлую работу в useLayoutEffect не кладут, на сервере layout его нет.
  - id: "sree-wealth.3b"
    label: "3b"
    topic: "Хуки: useEffect и useLayoutEffect"
    title: "Если логику можно написать прямо в функции, которая выполняется до рендера, зачем useLayoutEffect? Есть ли конкретный случай?"
    body: |
      #### Короткий ответ

      Функция компонента выполняется до коммита. DOM этого кадра ещё не записан, а render должен оставаться чистым: из тех же props и state выходит тот же JSX, без чтения свежей геометрии и без setState ради поправки.

      Ref на узел в этот момент часто ещё пустой или указывает на прошлый кадр. В Strict Mode render могут вызвать дважды, так что побочный эффект внутри него особенно плох.

      useLayoutEffect запускается, когда React уже записал новые узлы и браузер ещё не нарисовал кадр. Ты читаешь актуальную геометрию. Если из неё нужен setState, React успевает применить поправку до paint.

      Конкретный случай — тултип. Якорь уже в документе, подсказку нужно поставить под него и не показать кадр в координатах 0,0. В useLayoutEffect ты читаешь оба прямоугольника. Если снизу места нет, ставишь подсказку над якорем. `top` записывается до paint.

      Если число считается только из props и state, без DOM, его считают прямо в render. Эффект там не нужен.

      #### Пример кода

      ```tsx
      import { useLayoutEffect, useRef, useState } from 'react';

      function Tooltip({ anchorRef }) {
        const tipRef = useRef(null);
        const [top, setTop] = useState(0);

        useLayoutEffect(() => {
          const anchorBox = anchorRef.current.getBoundingClientRect();
          const tipBox = tipRef.current.getBoundingClientRect();
          const fitsBelow = anchorBox.bottom + 8 + tipBox.height < window.innerHeight;

          setTop(fitsBelow ? anchorBox.bottom + 8 : anchorBox.top - tipBox.height - 8);
        }, [anchorRef]);

        return (
          <div ref={tipRef} style={{ position: 'fixed', top }}>
            Hint
          </div>
        );
      }
      ```

      #### Фраза на автомате

      В теле компонента DOM этого коммита ещё нет, а render должен быть чистым. useLayoutEffect читает уже записанные узлы и успевает поправить state до paint. Пример: поставить тултип под якорь, чтобы он не мигнул в нулевых координатах. Без DOM ту же математику оставляю в render.
  - id: "sree-wealth.4a"
    label: "4a"
    topic: "Хуки: useState и useReducer"
    title: "useState ты знаешь. Зачем тогда появился useReducer, если state уже можно хранить через useState?"
    body: |
      #### Короткий ответ

      useState хранит значение и даёт setter. Это удобно, когда поля независимы: открыта ли панель, строка поиска, счётчик.

      useReducer появился для перехода, который трогает несколько связанных полей сразу. Событие «добавить позицию» и дописывает список, и сбрасывает ошибку. Эти правила живут в одной чистой функции, а не размазаны по обработчикам. Компонент шлёт действие, reducer возвращает следующее состояние.

      Dispatch у useReducer стабилен между рендерами. Reducer можно вызвать отдельно от компонента и проверить, что из пары state и action выходит ожидаемый объект.

      Независимые поля оставляют в useState. Связанный переход собирают в reducer, чтобы нельзя было обновить одно поле и забыть второе.

      #### Пример кода

      ```tsx
      import { useReducer } from 'react';

      function reducer(state, action) {
        switch (action.type) {
          case 'add':
            return {
              ...state,
              items: [...state.items, action.item],
              error: null,
            };
          case 'fail':
            return { ...state, error: action.message };
          default:
            return state;
        }
      }

      function Cart() {
        const [state, dispatch] = useReducer(reducer, { items: [], error: null });

        return (
          <button type="button" onClick={() => dispatch({ type: 'add', item: 'AAPL' })}>
            {state.items.length}
          </button>
        );
      }
      ```

      #### Фраза на автомате

      useState — для независимых значений. useReducer — когда одно действие меняет несколько связанных полей: правила лежат в чистой функции, компонент шлёт action, dispatch стабилен. Функцию можно проверить без рендера.
  - id: "sree-wealth.4b"
    label: "4b"
    topic: "Хуки: useState и useReducer"
    title: "Логику обновления всё равно нужно где-то написать, её просто переносят в reducer. В чём тогда реальная польза useReducer по сравнению с useState?"
    body: |
      #### Короткий ответ

      Польза не в том, что строк становится меньше. Польза в том, что переход видит весь state и одно действие.

      Два setter-а могут обновить статус и забыть сбросить ошибку. Тогда на экране одновременно «сохраняем» и старый текст ошибки. Reducer на `submit` записывает оба поля в одном возврате, невозможная пара не собирается по кускам в разных обработчиках.

      Второе: reducer — чистая функция. Ты вызываешь `reducer(state, action)` в тесте без дерева React. Та же логика, разложенная по onClick, проверяется только через рендер.

      Третье: один dispatch вместо нескольких setter-ов, и ссылка на dispatch не меняется от рендера к рендеру. Её спокойно передают вниз.

      React и так группирует несколько setState в одном обработчике. Группировка не заменяет общие правила: она только склеивает обновления по времени.

      #### Пример кода

      ```tsx
      function reducer(state, action) {
        switch (action.type) {
          case 'submit':
            return { ...state, status: 'saving', error: null };
          default:
            return state;
        }
      }

      // reducer({ status: 'idle', error: 'Try again' }, { type: 'submit' })
      // => { status: 'saving', error: null }
      ```

      #### Фраза на автомате

      Код никуда не исчезает, он собирается в одну чистую функцию. Одно действие видит весь state и меняет связанные поля вместе, это можно вызвать в тесте без рендера. Несколько useState легко обновляют одно поле и забывают второе. Стабильный dispatch удобно передавать вниз.
  - id: "sree-wealth.4c"
    label: "4c"
    topic: "Хуки: useState и useReducer"
    title: "Что именно ты называешь «сложным state» в этом контексте?"
    body: |
      #### Короткий ответ

      Сложный state здесь — связанные поля, которые должны меняться одним переходом. Следующее значение зависит от предыдущей формы, и частичное обновление даёт невозможную комбинацию.

      Пример: шаг мастера, черновик и список ошибок. Событие «отправить» переводит шаг, чистит ошибки и ставит статус. Если обновить только шаг, на экране останется ошибка прошлого шага.

      Сюда же вложенное обновление: переключить элемент внутри списка и вместе сбросить выделение, если фильтр изменился.

      Не это: один boolean модалки, счётчик, одна строка инпута. Большой объект, который ты целиком заменяешь и чьи поля друг на друга не влияют, тоже не становится сложным от размера. Много вызовов useState сами по себе не делают state сложным, если значения независимы.

      #### Пример кода

      ```tsx
      type EditorState = {
        step: 'draft' | 'review';
        draft: string;
        errors: string[];
      };
      ```

      #### Фраза на автомате

      Сложный state — это связанные поля одного перехода: шаг, черновик и ошибки, которые нельзя обновлять по отдельности. Независимые boolean, счётчик и одна строка остаются в useState. Размер объекта сам по себе сложность не создаёт.
  - id: "sree-wealth.5a"
    label: "5a"
    topic: "Хуки: useRef"
    title: "Знаешь useRef? Чем он отличается от state?"
    body: |
      #### Короткий ответ

      useRef возвращает объект `{ current }`, который живёт от рендера к рендеру. Запись в `current` не ставит новый рендер. State при обновлении как раз ставит рендер, и UI читает новое значение на следующем проходе.

      Ref держат для DOM-узла, id таймера, предыдущего значения и любой ячейки, от которой разметка не должна обновляться сама. Счётчик рендеров в ref можно увеличить во время render: экран из-за этой записи не перерисуется.

      Значение, которое пользователь должен увидеть, хранят в state. Читать ref во время render, чтобы из него построить JSX, значит нарисовать данные, об изменении которых React не узнает.

      #### Пример кода

      ```tsx
      import { useRef, useState } from 'react';

      function SearchBox() {
        const inputRef = useRef(null);
        const [query, setQuery] = useState('');
        const renders = useRef(0);

        renders.current += 1;

        return (
          <input
            ref={inputRef}
            value={query}
            onChange={(event) => setQuery(event.target.value)}
          />
        );
      }
      ```

      #### Фраза на автомате

      useRef — это ячейка `{ current }` между рендерами. Запись в неё не вызывает рендер. State вызывает. В ref кладу DOM-узел, таймер и всё, от чего UI не должен обновляться сам. То, что видно на экране, держу в state.
  - id: "sree-wealth.5b"
    label: "5b"
    topic: "Хуки: useRef"
    title: "Можно ли заставить useRef вести себя как useState? Это возможно?"
    body: |
      #### Короткий ответ

      Как замена useState — нет. Запись в `ref.current` не ставит обновление. Экран остаётся прежним, пока рендер не запустит что-то другое.

      ```tsx
      import { createContext, useContext, useState } from 'react';

      const ThemeContext = createContext('light');

      function App() {

        return (
          <ThemeContext.Provider value={theme}>
            <Toolbar onToggle={() => setTheme('dark')} />
          </ThemeContext.Provider>
        );
      }

      function Toolbar({ onToggle }) {
        const theme = useContext(ThemeContext);

        return (
          <button type="button" onClick={onToggle}>
            {theme}
          </button>
        );
      }
      ```

      #### Фраза на автомате

      Context передаёт значение вниз без prop drilling. Provider публикует value, useContext его читает. При смене value потребители этого контекста рендерятся снова. Вне Provider остаётся значение по умолчанию. Для темы, локали и сессии этого хватает.

      #### Короткий ответ

      ```tsx
      import { createContext, useContext, useReducer } from 'react';

          default:
            return state;
        }
      }

        const [state, dispatch] = useReducer(reducer, { count: 0 });

        return (
          <StoreContext.Provider value={{ state, dispatch }}>
            {children}
          </StoreContext.Provider>
        );
      }

      function Counter() {
        const { state, dispatch } = useContext(StoreContext);

        return (

            {state.count}
          </button>
        );
      }
      ```

      Да, базовое поведение собирается из useReducer и Context: один state, dispatch, чтение где угодно под Provider. Middleware, DevTools и подписка на срез в Context не входят. Dispatch сразу попадает в reducer, а новый state будит всех потребителей этого value.

    title: "Что это за соглашение о версиях? Знаешь semantic versioning? Что это?"
    body: |
      #### Короткий ответ

      Это semantic versioning, SemVer. Номер версии состоит из трёх чисел: MAJOR.MINOR.PATCH.

      MAJOR увеличивают, когда меняется контракт и старый потребитель ломается. MINOR — когда появляется возможность и старый код остаётся рабочим. PATCH — когда исправление не меняет контракт. Пример: `4.17.21`, затем исправление `4.17.22`, новая возможность `4.18.0`, ломающее изменение `5.0.0`.

      В requiredVersion пишут не одну точку, а диапазон. `^4.17.21` принимает версию не ниже `4.17.21` и ниже `5.0.0`. `~4.17.21` принимает только patch: не ниже `4.17.21` и ниже `4.18.0`.

      Для общей библиотеки в Module Federation как раз нужен такой диапазон: совместимые 4.x делят один singleton, мажор 5 уже другой контракт.

      #### Фраза на автомате

      Semantic versioning — это MAJOR.MINOR.PATCH. Мажор ломает потребителей, минор добавляет совместимое, патч чинит. `^4.17.21` пускает совместимые 4.x и останавливается перед 5. В requiredVersion стоит такой диапазон, а не одна жёсткая точка.

На экране строка `Showing X–Y of 100 posts`, кнопки `Previous`, `Next` и номера страниц. `Previous` недоступна на первой странице, `Next` недоступна на последней.

      Номер страницы зажимается в новый диапазон, когда размер растёт. Иначе страница 10 при размере 10 после переключения на 20 указывает за конец массива, и срез пустой.

      #### Пример кода

      ```tsx
      // Reconstruction of the task. Not a transcript of the candidate's screen.

      import { useEffect, useState } from 'react';

      type Post = {
        id: number;
        title: string;
      };

      const PAGE_SIZES = [10, 20, 30];

      function usePagedPosts() {
        const [posts, setPosts] = useState<Post[]>([]);
        const [status, setStatus] = useState<'loading' | 'ready' | 'error'>('loading');
        const [page, setPage] = useState(1);
        const [pageSize, setPageSize] = useState(10);

        useEffect(() => {
          const controller = new AbortController();

          fetch('https://jsonplaceholder.typicode.com/posts', {
            signal: controller.signal,
          })
            .then((response) => {
              if (!response.ok) {
                throw new Error('Request failed');
              }

              return response.json();
            })
            .then((data: Post[]) => {
              setPosts(data);
              setStatus('ready');
            })
            .catch((error: { name?: string }) => {
              if (error.name === 'AbortError') {
                return;
              }

              setStatus('error');
            });

          return () => controller.abort();
        }, []);

        const pageCount = Math.max(1, Math.ceil(posts.length / pageSize));
        const safePage = Math.min(page, pageCount);
        const start = (safePage - 1) * pageSize;
        const pageItems = posts.slice(start, start + pageSize);
        const from = pageItems.length === 0 ? 0 : start + 1;
        const to = start + pageItems.length;

        const handlePageSize = (nextSize: number) => {
          const nextCount = Math.max(1, Math.ceil(posts.length / nextSize));

          setPageSize(nextSize);
          setPage((current) => Math.min(current, nextCount));
        };

        return {
          status,
          pageItems,
          page: safePage,
          pageCount,
          pageSize,
          from,
          to,
          setPage,
          handlePageSize,
        };
      }

      export default function PostsPage() {
        const {
          status,
          pageItems,
          page,
          pageCount,
          pageSize,
          from,
          to,
          setPage,
          handlePageSize,
        } = usePagedPosts();

        if (status === 'loading') {
          return <p>Loading…</p>;
        }

        if (status === 'error') {
          return <p>Failed to load posts</p>;
        }

        return (
          <section>
            <label htmlFor="page-size">Items per page</label>
            <select
              id="page-size"
              value={pageSize}
              onChange={(event) => handlePageSize(Number(event.target.value))}
            >
              {PAGE_SIZES.map((size) => (
                <option key={size} value={size}>
                  {size}
                </option>
              ))}
            </select>

            <p>{`Showing ${from}–${to} of 100 posts`}</p>

            <ul>
              {pageItems.map((post) => (
                <li key={post.id}>{post.title}</li>
              ))}
            </ul>

            <button type="button" onClick={() => setPage(page - 1)} disabled={page === 1}>
              Previous
            </button>

            {Array.from({ length: pageCount }, (_, index) => {
              const number = index + 1;

              return (
                <button
                  key={number}
                  type="button"
                  onClick={() => setPage(number)}
                  aria-current={number === page ? 'page' : undefined}
                >
                  {number}
                </button>
              );
            })}

            <button
              type="button"
              onClick={() => setPage(page + 1)}
              disabled={page === pageCount}
            >
              Next
            </button>
          </section>
        );
      }
      ```

      #### Фраза на автомате

      Один fetch постов JSONPlaceholder, список из state, кастомный хук режет их на клиенте. Размер 10, 20 или 30, строка Showing X–Y of 100 posts, кнопки Previous, Next и номера. Previous выключена на первой, Next на последней. При смене размера номер страницы зажимается в новый диапазон.

      #### Короткий ответ

      Axios поставить можно, если среда разрешает `npm install axios`. Для JSONPlaceholder хватает `fetch`: один GET и JSON, без новой зависимости. На установку лучше спросить до команды. У Axios тело лежит в `response.data`, у fetch его ещё нужно прочитать через `response.json()`. Пагинация от клиента не зависит.

      Уже собрано: запрос `https://jsonplaceholder.typicode.com/posts`, посты в state, кастомный хук режет массив на клиенте, размер страницы 10, 20 или 30, строка `Showing X–Y of 100 posts`, кнопки `Previous`, `Next` и номера. `Previous` недоступна на первой странице, `Next` недоступна на последней.

      Проверка идёт при размере 10. Постов 100, страниц 10. Клики по странице 2, потом 10, потом 9, потом `Next` оставляют номер 10. Этот номер при размере 10 законный: это последняя страница, элементы 91–100.

      Затем в списке выбирают 20. Страниц становится 5, потому что 100 / 20 = 5. Номер 10 для нового размера уже вне диапазона 1–5.

      Если номер не зажать, старт считается как `(10 - 1) * 20 = 180`. В массиве индексы 0–99, `slice(180, 200)` пустой. Подпись выходит бессмысленной: `Showing 181–180 of 100 posts`. Чтение `posts[180]` бросает ошибку. Кнопка `Next` при сравнении `page === pageCount` (`10 === 5`) остаётся включённой.

      Это ошибка логики. Номер страницы пережил смену размера и указывает на страницу, которой больше нет. После смены размера его ограничивают новым числом страниц: `Math.min(page, pageCount)`. Сброс на 1 тоже убирает ошибку.

      Пример — реконструкция условия, не экран кандидата.
